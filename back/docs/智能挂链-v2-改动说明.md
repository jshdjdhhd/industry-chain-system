# 智能挂链 V2 改动说明

## 背景

V1 版本已经完成了基于关键词、经营范围、主营产品、节点路径等字段的本地规则匹配，可以在真实企业库和产业链节点库上生成可解释的挂链推荐。

V2 的目标是在保留 V1 可解释能力的基础上，引入 embedding 向量语义检索，让系统能够处理「企业描述和节点关键词不完全一致，但语义相关」的场景。例如企业名称、主营业务、经营范围和产业链节点名称不直接命中时，仍然可以通过语义相似度召回候选节点。

## 改动范围

本次只改动后端智能挂链相关代码，未修改前端。

主要改动包括：

- 新增本地 Ollama + Qwen3 Embedding 的向量生成客户端。
- 新增企业和产业链节点的完整画像文本构建逻辑。
- 新增向量缓存表 `ai_embedding_vector`，避免重复调用本地 embedding 服务。
- 新增 V2 混合匹配 Provider：向量相似度召回 + V1 规则分数融合。
- 调整匹配任务记录的 `model_name`，从硬编码 `RULE_BASED` 改为由实际 Provider 返回。
- 补充 embedding、混合匹配、配置默认值、测试库 schema 的测试覆盖。

## 核心实现

### 1. 完整画像文本构建

新增 `EmbeddingProfileTextBuilder`，不再只拿短关键词做 embedding，而是构造更完整的语义输入。

企业画像包含：

- 企业名称；
- 经营范围；
- 主营产品与技术关键词；
- 企业标签；
- 本地域词扩展结果。

节点画像包含：

- 节点路径；
- 节点名称；
- 节点关键词；
- 节点定义；
- 本地域词扩展结果。

这样做的原因是 embedding 对短文本很敏感，单独比较「苹果」和「手机」或「中际旭创」和「光模块」时，小模型容易判断不稳定。将业务字段组织成完整画像后，模型能获得更多上下文。

### 2. 本地域词扩展

新增 `LocalDomainTermExpander`，用于补充行业常识词，提升短文本和企业简称的匹配稳定性。

典型例子：

- `中际旭创` 会扩展到光模块、光通信、光器件等相关词；
- `苹果` 会扩展到手机、智能手机、iPhone、消费电子等相关词；
- `宁德时代` 会扩展到动力电池、锂电池、电芯、储能电池等相关词。

这不是 mock 数据，也不是替代真实数据库，而是 embedding 输入文本的领域增强策略。

### 3. 本地 Qwen3 Embedding 接入

新增 `LocalQwenEmbeddingClient`，通过 Ollama 的 OpenAI-compatible `/v1/embeddings` 接口生成向量。

默认配置：

```yaml
matching:
  embedding:
    endpoint: ${LOCAL_EMBEDDING_ENDPOINT:http://localhost:11434/v1/embeddings}
    model: ${LOCAL_EMBEDDING_MODEL:qwen3-embedding:0.6b}
    dimension: ${LOCAL_EMBEDDING_DIMENSION:1024}
```

实际运行前需要本机 Ollama 已安装并拉取模型：

```powershell
ollama pull qwen3-embedding:0.6b
```

### 4. 向量缓存

新增 `EmbeddingVectorService`，负责生成和复用向量。

缓存策略：

- 使用 `object_type + object_id + model_name` 定位对象向量；
- 使用画像文本的 SHA-256 作为 `text_hash`；
- 如果对象、模型和文本 hash 都一致，直接复用历史向量；
- 如果画像文本变化，逻辑删除旧向量，重新生成并保存新向量。

这样可以避免每次创建推荐任务时都重复生成企业和节点向量，减少本地推理耗时。

### 5. 数据库迁移

新增迁移脚本：

```text
src/main/resources/db/migration/V6__ai_embedding_vector.sql
```

新增表：

```text
ai_embedding_vector
```

关键字段：

- `object_type`：对象类型，当前支持 `ENTERPRISE` 和 `CHAIN_NODE`；
- `object_id`：对象 ID；
- `model_name`：embedding 模型名称；
- `dimension`：向量维度；
- `text_hash`：画像文本 SHA-256；
- `vector_data`：向量 JSON 数组；
- `source_text_snapshot`：生成向量时使用的画像文本快照；
- `is_deleted`：逻辑删除标记。

由于当前数据库是 MySQL 5.7，没有原生向量类型，所以向量用 `LONGTEXT` 存储 JSON 数组。后续如果升级到支持向量索引的数据库，可以把这一层替换为数据库原生向量检索。

### 6. 混合匹配算法

新增 `HybridEmbeddingMatchingProvider`，并通过 `@Primary` 作为默认 `MatchingProvider`。

流程如下：

1. 从真实数据库读取企业信息和产业链节点。
2. 构建企业完整画像文本。
3. 生成或读取企业 embedding 向量。
4. 遍历当前产业链下的节点，构建节点画像文本。
5. 生成或读取节点 embedding 向量。
6. 计算企业向量和节点向量的余弦相似度。
7. 调用 V1 规则匹配，获取规则置信度和证据。
8. 融合向量分数和规则分数，得到最终推荐分。
9. 按最终分数排序，返回 Top K 推荐结果。

当前默认融合公式：

```text
final_score = vector_weight * vector_similarity + rule_weight * rule_confidence
```

默认权重：

```yaml
vector-weight: 0.70
rule-weight: 0.30
min-vector-score: 0.25
top-k: 5
```

V2 的推荐结果会保留可解释 evidence，包含：

- `model`：模型标识，当前为 `HYBRID_EMBEDDING_V2`；
- `vector_similarity`：向量相似度；
- `rule_confidence`：V1 规则置信度；
- `final_score`：融合后的最终分；
- `enterprise_profile`：企业画像文本；
- `node_profile`：节点画像文本；
- `rule_evidence`：V1 规则匹配证据。

## 对原有逻辑的调整

### 匹配任务模型名

`MatchingServiceImpl` 不再把 `matching_task.model_name` 固定写死为 `RULE_BASED`，而是调用 `matchingProvider.getModelName()`。

这样 V1、V2、后续 V3 大模型版本都可以在任务表里留下真实模型标识，方便排查和复盘。

### 节点路径

`ChainNodeQueryServiceImpl` 构建匹配用节点信息时，会使用 `buildNodePath(node.getId())` 得到可读的完整节点路径。这样节点画像不仅有节点名称，也有产业链层级位置。

## 本地联调注意事项

1. 本地需要安装 Ollama。
2. 需要拉取 embedding 模型：

```powershell
ollama pull qwen3-embedding:0.6b
```

3. 确认 Ollama 服务可访问：

```powershell
Invoke-RestMethod -Uri "http://localhost:11434/api/tags" -Method Get
```

4. 后端本地配置文件 `application-local.yml` 已加入 `.gitignore`，不要提交真实数据库账号密码。
5. 如果要切换模型或端口，只需要改环境变量或本地配置：

```text
LOCAL_EMBEDDING_ENDPOINT
LOCAL_EMBEDDING_MODEL
LOCAL_EMBEDDING_DIMENSION
MATCHING_VECTOR_WEIGHT
MATCHING_RULE_WEIGHT
MATCHING_MIN_VECTOR_SCORE
MATCHING_TOP_K
```

## 后续可优化方向

- 增加后台预热任务，提前生成企业和节点向量，减少首次推荐延迟。
- 引入批量 embedding，减少逐节点 HTTP 调用次数。
- 如果数据库升级到支持向量索引的版本，可将 `LONGTEXT` 向量缓存升级为原生向量列。
- V3 可以在 V2 Top K 结果之后接入大模型 rerank，让大模型基于 evidence 做二次判断和解释生成。
- 领域扩展词后续可以从行业词库表维护，而不是写在代码中。
