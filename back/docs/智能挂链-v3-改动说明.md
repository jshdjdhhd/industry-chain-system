# 智能挂链 V3 改动说明

## 背景

V2.1 已经完成本地 `Qwen3 Embedding` 语义召回、规则融合、领域词库扩展和离线评估能力，但最终排序仍主要依赖向量相似度与规则分。V3 在此基础上增加大模型重排序（LLM Rerank）：先由 V2.1 召回候选节点，再交给大模型做候选内精排、推荐理由生成和风险提示。

本版本默认对接小米 MiMo 的 OpenAI-compatible `chat/completions` 接口，同时把调用层抽象成通用 LLM 客户端，后续切换阿里云、OpenAI-compatible 私有模型或其他厂商时，只需要替换配置。

## 核心链路

```text
企业 ID + 产业链 ID
        ↓
V2.1 HybridEmbeddingMatchingProvider 召回 Top 10 候选
        ↓
组装企业画像、候选节点画像、向量分、规则分、V2.1 排名
        ↓
MiMo 大模型 JSON 重排序
        ↓
返回 Top 5：节点 ID、置信度、推荐理由、风险点
        ↓
写入 matching_task / matching_result
```

## 主要改动

- 新增 `matching.llm` 配置组，默认使用 MiMo：
  - `provider=mimo`
  - `base-url=https://api.xiaomimimo.com/v1`
  - `model=mimo-v2.5-pro-ultraspeed`
  - `api-key=${MATCHING_LLM_API_KEY:}`
  - `candidate-top-k=10`
  - `result-top-k=5`
- 新增通用 LLM 适配层：
  - `LlmClient`：大模型调用抽象。
  - `OpenAiCompatibleLlmClient`：OpenAI-compatible HTTP 实现。
  - `LlmHttpTransport`：HTTP 传输抽象，便于单元测试和后续替换。
- 新增 `LlmRerankMatchingProvider`，并作为默认 `MatchingProvider`：
  - `model_name = LLM_RERANK_V3`。
  - 正常情况使用大模型排序结果。
  - 大模型失败、超时、JSON 非法或未配置 API Key 时，自动回退 V2.1。
- 扩展 `HybridEmbeddingMatchingProvider`：
  - 保留原 `match(enterpriseId, chainId)` 行为。
  - 新增 `matchCandidates(enterpriseId, chainId, topK)`，供 V3 获取更多候选。
- 新增 prompt 与 JSON 解析：
  - Prompt 只允许大模型在候选节点内排序，不允许编造 `node_id`。
  - 输出格式固定为 `ranked_results` 数组。
  - 解析时过滤未知节点、重复节点和非法 JSON。

## 项目适配增强

本版本没有做模型微调（fine-tuning），而是先采用成本更低、上线更快、可控性更强的项目级 prompt 优化。原因是微调需要稳定的标注样本、评估集和模型版本管理；当前阶段更适合先用真实业务数据积累采纳、拒绝和人工修正样本。

V3 的大模型 prompt 已经针对本项目做了以下适配：

- **项目上下文：** 明确任务是“产业链智能挂链”，目标是把企业挂接到最合适的产业链节点，而不是泛泛的行业分类。
- **评分规则：** 要求大模型按主营产品与核心技术、产业链上下游环节、节点关键词与领域扩展词、V2.1 分数一致性、误挂风险这 5 个维度判断。
- **Few-shot 示例：** 内置中际旭创、宁德时代、苹果等典型样例，帮助模型理解“光模块”“动力电池”“智能终端整机”等挂链边界。
- **领域词提示：** 从企业画像和前 3 个强候选节点的 `领域扩展词` 中提取术语，注入 prompt，增强模型对项目领域词库的理解。
- **置信度校准：** 约束高、中、低分区间，避免大模型随意给高置信度。
- **版本追踪：** `evidence` 中记录 `prompt_version` 和 `prompt_profile`，便于后续对比不同 prompt 策略的效果。

这套方案的定位是“项目适配型大模型重排序”，不是裸调 API。它保留 V2.1 的召回能力和工程兜底，同时让大模型更懂当前项目里的产业链节点、行业术语和推荐边界。

## 结果与证据字段

V3 继续复用原有结果表，不新增数据库表。

- `matching_task.model_name` 写入 `LLM_RERANK_V3`。
- `matching_result.reason` 写入大模型生成的推荐理由。
- `matching_result.confidence` 写入大模型置信度。
- 远程联调库当前 `matching_result.reason/evidence` 为 `varchar(1000)`，因此服务层会在写入前压缩超长字段，避免大模型证据 JSON 过长导致接口 500。
- `matching_result.evidence` 写入压缩后的关键证据 JSON，主要包含：
  - `model`
  - `prompt_version`
  - `prompt_profile`
  - `llm_provider`
  - `llm_model`
  - `llm_fallback`
  - `llm_confidence`
  - `risk`
  - `v21_confidence`
  - `vector_similarity`
  - `rule_confidence`
  - `v21_final_score`

当大模型不可用时，`evidence.llm_fallback=true`，推荐顺序与分数沿用 V2.1，同时记录 `fallback_model=HYBRID_EMBEDDING_V2`。

当候选均低于自动推荐阈值时，V3 不再返回空结果，而是返回低置信候选供人工复核。此时会跳过 LLM 调用，在 `evidence` 中写入 `recommendation_level=LOW_CONFIDENCE`、`below_min_result_confidence=true` 和 `llm_skipped=true`，前端据此提示“不建议自动挂链”。

查询接口会把证据字段转换成前端更容易展示的可读摘要，例如“语义相似度”“规则置信度”等；原始压缩 JSON 仍保留在数据库中用于排查。

## 配置与安全

真实 API Key 不允许写入仓库，也不要写入提交记录、文档或日志。联调时使用环境变量或本地 ignored 配置：

```yaml
matching:
  llm:
    api-key: ${MATCHING_LLM_API_KEY:}
```

切换厂商时，优先改配置，不改业务代码：

```yaml
matching:
  llm:
    provider: other-openai-compatible-provider
    base-url: https://example.com/v1
    model: your-model-name
    api-key: ${MATCHING_LLM_API_KEY:}
```

## 面试讲法

V3 没有让大模型直接扫描数据库，而是采用“召回 + 重排序”的推荐系统架构。V2.1 负责从真实数据库画像中召回高相关候选，保证检索效率和覆盖率；V3 只把 Top K 候选交给大模型判断，降低 token 成本、响应时间和幻觉风险。

这种设计同时保留了工程兜底：大模型失败时自动回退 V2.1，业务流程仍能返回稳定推荐；结果证据中保留向量分、规则分、V2.1 原始证据和大模型解释，方便前端展示、队友排查和后续离线评估。

项目适配层面可以重点讲：我没有直接把大模型当成黑盒推荐器，而是为产业链挂链任务设计了项目级 prompt，包括业务目标、评分维度、few-shot 示例、领域词提示和置信度校准，并把 prompt 版本写入 evidence，方便后续用离线评估样本做 A/B 对比。
