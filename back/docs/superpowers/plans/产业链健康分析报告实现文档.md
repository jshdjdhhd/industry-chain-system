# 13 产业链健康分析报告实现文档

## 1. 实现目标

本文档基于 `12-产业链健康分析报告设计.md`，结合当前后端 `groupprojectback/back` 与前端 `groupprojectfront/front` 源码，说明第一版“产业链 G6 可视化树图 + 健康度分析报告”的落地方案。

第一版目标：

- 新增产业链 G6 可视化页面，平时用于浏览产业链结构。
- G6 节点由后端实时计算健康度，前端只负责颜色、大小、标签渲染。
- 点击“创建报告”后进入节点选择模式，选中父节点即默认分析整棵子树。
- 新增独立 `analysis` 后端模块，创建异步健康分析报告任务。
- 报告采用实时结构化 RAG，从现有业务表查询节点、挂链关系、企业画像、历史推荐证据并组装上下文。
- 大模型只基于后端输入材料生成 Markdown 解释，不修改健康分。
- Markdown 作为源格式，HTML 用于预览，PDF 用于下载。

明确不做：

- 不做外部企业补链推荐。
- 不做招商候选企业池。
- 不做 What-if 模拟推演。
- 不新增独立知识库表。
- 不新增健康度结果表。

```text
  ├─ 现有业务表：chain / chain_node / enterprise / enterprise_node_rel / tag / matching_result
```

模块边界：

- `analysis` 只读取现有产业链、企业、挂链、推荐证据数据，不改写智能挂链主流程。

- 健康度只由 `ChainHealthMetricService` 规则计算，大模型只能解释。

### 4.2 LLM 通用模块复用

最新后端已完成 LLM 拆分，不需要健康分析报告模块再迁移 `matching/llm`。

当前包结构：

| 包 | 内容 | 健康报告使用方式 |
| --- | --- | --- |
| `git.ggwzz.llm` | `LlmClient`、`OpenAiCompatibleLlmClient`、`LlmMessage`、`LlmChatCompletion`、`LlmProperties`、HTTP transport | 直接注入并调用 |
| `git.ggwzz.matching.llm` | `MatchingLlmProperties`、`LlmRerankDecision`、`LlmRerankPromptBuilder`、`LlmRerankResultParser` | 智能挂链专用，报告模块不依赖 |

配置口径：

```properties
llm.base-url=...
llm.model=...
llm.api-key=...
llm.timeout-seconds=20
llm.temperature=0
llm.max-tokens=700

matching.llm.result-top-k=3
matching.llm.min-result-confidence=0.65
```

报告模块只使用 `llm.*` 通用配置，不读取 `matching.llm.*` 阈值。

报告正文通常比挂链重排响应更长，联调环境可按报告长度适当调高 `llm.max-tokens`，例如 3000-6000；如果担心影响智能挂链响应长度，先通过报告上下文压缩控制输出规模。

调用方式：

```java
import git.ggwzz.llm.LlmChatCompletion;
import git.ggwzz.llm.LlmClient;
import git.ggwzz.llm.LlmMessage;

@RequiredArgsConstructor
@Service
public class AnalysisReportWorker {

    private final LlmClient llmClient;
    private final AnalysisReportResultParser resultParser;

    public String generateMarkdown(String systemPrompt, String userPrompt) {
        LlmChatCompletion result = llmClient.complete(List.of(
                new LlmMessage("system", systemPrompt),
                new LlmMessage("user", userPrompt)
        ));
        return resultParser.parseMarkdown(result.content());
    }
}
```

实现要求：

- `analysis` 通过 `git.ggwzz.llm.LlmClient` 调用大模型。
- 报告生成不使用 `MatchingProvider`、`MatchingServiceImpl`。
- 不依赖 `MatchingLlmProperties` 中的挂链重排阈值。
- 当前 `OpenAiCompatibleLlmClient` 请求体仍设置 `response_format=json_object`，因此报告提示词建议要求模型返回 JSON 对象，例如 `{"markdown":"# 报告..."}`，由 `AnalysisReportResultParser` 提取 `markdown` 字段后保存为 `content_markdown`。
- 如果后续通用 LLM 客户端增加自由文本模式，可将报告链路切换为直接返回 Markdown；第一版以现有 `LlmClient.complete(...)` 为准。

### 4.4 健康度计算

新增 `ChainHealthMetricService`，输入为产业链节点列表、直接企业数、子树企业数、企业质量聚合、同级分组信息，输出每个节点的健康指标。

VO 建议：

```java
public class DiagnosisTreeNodeVO {
    private Long nodeId;
    private String nodeName;
    private String nodePath;
    private Integer nodeLevel;
    private String keywords;
    private String description;
    private Integer directEnterpriseCount;
    private Integer subtreeEnterpriseCount;
    private Integer healthScore;
    private String healthLevel;
    private String healthLabel;
    private List<String> weakReasons;
    private List<DiagnosisTreeNodeVO> children;
}
```

第一版评分口径：

```text
节点健康分 = 企业承载得分 * 0.50
          + 单点依赖得分 * 0.25
          + 同级均衡得分 * 0.15
          + 企业质量得分 * 0.10
```

可执行规则建议：

| 指标 | 计算方式 |
| --- | --- |
| 企业承载得分 | 子树有效企业数 `0=0`、`1=25`、`2-3=50`、`4-7=75`、`>=8=100` |
| 单点依赖得分 | 子树有效企业数 `0=0`、`1=20`、`2=50`、`3-4=75`、`>=5=100` |
| 同级均衡得分 | 当前子树数 / 同父节点平均子树数；`>=1=100`、`0.7-1=80`、`0.4-0.7=55`、`0-0.4=25`，同级全空时给 50 |
| 企业质量得分 | 子树企业中有产值、税收、重点标签、主营产品/核心技术的比例综合，缺失不重罚，默认最低 40；无企业为 0 |

等级：

| 条件 | 等级 | 标签 |
| --- | --- | --- |
| `subtreeEnterpriseCount == 0` | `EMPTY` | 空白 |
| `score >= 80` | `HEALTHY` | 健康 |
| `score >= 60` | `NORMAL` | 一般 |
| `score >= 30` | `WEAK` | 偏弱 |
| `score >= 1` | `RISK` | 风险 |

弱项原因示例：

- `EMPTY`：`该节点及子树暂无已挂载企业`
- 企业承载得分低：`子树企业承载偏低`
- 单点依赖得分低：`存在单点依赖风险`
- 同级均衡得分低：`明显低于同级平均企业承载`
- 企业质量得分低：`企业产值、税收或画像信息不足`

### 4.5 诊断树接口

新增控制器：

```java
@RestController
@RequestMapping("/api/analysis/chains")
public class ChainDiagnosisController {
    @GetMapping("/{chainId}/diagnosis-tree")
    @PreAuthorize("hasAuthority('analysis:diagnosis:query') or hasAuthority('chain:node:query')")
    public Result<DiagnosisTreeNodeVO> getDiagnosisTree(@PathVariable Long chainId) {
        return Result.success(chainDiagnosisTreeService.getDiagnosisTree(chainId));
    }
}
```

实现步骤：

1. 校验 `chain` 存在。
2. 查询 `chain_node` 下全部未删除节点。
3. 查询每个节点直接企业数。
4. 用节点 `node_path` 批量统计子树企业数和企业质量聚合。
5. 计算健康分和等级。
6. 按 `parent_id` 组装树。
7. 返回虚拟根节点或一级节点数组。建议返回虚拟根节点，便于前端 G6 以产业链名称作为根。

性能建议：

- 不要对每个节点单独查一次子树企业。
- 使用一次 SQL 按祖先节点聚合，或先取节点与关系后在内存中按 `node_path` 归并。
- 节点量较小时，内存归并更容易实现；正式数据量较大时，优先优化 XML 聚合 SQL。

请求 DTO：

```java
public class CreateAnalysisReportRequest {
    @NotNull
    private Long chainId;

    @NotBlank
    private String reportType;

    @NotBlank
    private String scopeType;

    private List<Long> nodeIds;

    private AnalysisReportOptions options;

```

校验规则：

- `reportType` 第一版只允许 `HEALTH_ANALYSIS`。
- `scopeType` 支持 `SELECTED_NODES`、`ALL_CHAIN`。
- `SELECTED_NODES` 时 `nodeIds` 不能为空。
- 所有 `nodeIds` 必须属于同一 `chainId`。
- 如果选择父节点，后端根据 `node_path` 展开完整子树，前端传来的只是用户选择口径。

任务创建流程：

```text
AnalysisReportService.createReport
  ├─ 参数校验
  ├─ resolveScope 展开子树节点
  ├─ 创建 analysis_report_task，status=PROCESSING
  ├─ 记录 @OperationLog
  └─ 调用 AnalysisReportWorker.execute(taskId)
```

任务执行流程：

```text
AnalysisReportWorker.execute
  ├─ 查询任务
  ├─ 构建诊断指标快照
  ├─ AnalysisReportContextBuilder 组装结构化上下文
  ├─ AnalysisReportPromptBuilder 生成提示词
  ├─ LlmClient.complete 调用通用大模型
  ├─ AnalysisReportResultParser 从 JSON 响应中提取 Markdown
  ├─ ReportExportService 渲染 HTML
  ├─ ReportExportService 导出 PDF
  ├─ 写入 analysis_report_content
  └─ 更新 task 为 COMPLETED 或 FAILED
```

重试流程：

- 仅允许 `FAILED`、`CANCELLED` 状态重试。
- 可创建新任务并设置 `retry_from_task_id`，也可原任务递增 `retry_count` 后重新执行。
- 为了历史清晰，建议创建新任务；如果页面要求“原地重试”，则详情页展示最新重试任务并保留来源关系。

### 4.7 RAG 上下文构建

`AnalysisReportContextBuilder` 只从现有结构化业务表读取数据。

上下文建议结构：

```json
{
  "chain": {
    "chainId": 1,
    "chainName": "家电生产产业链"
  },
  "scope": {
    "selectedNodeIds": [12, 15],
    "resolvedNodeIds": [12, 13, 14, 15],
    "scopeDescription": "上游：原材料与核心零部件等 4 个节点"
  },
  "metrics": {
    "summary": {
      "nodeCount": 4,
      "enterpriseCount": 18,
      "healthyCount": 1,
      "normalCount": 1,
      "weakCount": 1,
      "riskCount": 0,
      "emptyCount": 1
    },
    "nodes": []
  },
  "enterpriseSamples": [],
  "matchingEvidence": []
}
```

上下文控制：

- 风险、偏弱、空白节点优先进入报告。
- 企业样本总数设置上限，例如 50 家。
- 单节点企业样本设置上限，例如风险节点最多 15 家，健康节点最多 5 家。
- 不把未挂载企业放入上下文。
- 不引入外部政策、新闻、招商候选企业。

提示词约束：

```text
你只能基于输入材料生成产业链健康分析报告。
不得编造企业、节点、政策、市场事实或外部候选企业。
健康分由系统规则计算，你只能解释分数，不得修改分数。
报告正文使用 Markdown。
由于当前通用 LLM 客户端使用 json_object 响应格式，请只输出一个 JSON 对象：
{"markdown":"...Markdown 报告正文..."}
```

后端新增 `AnalysisReportResultParser`，只读取 `markdown` 字段；字段为空、不是 JSON 或正文为空时任务置为 `FAILED` 并保存错误原因。

报告建议结构：

```text
# {产业链名称}健康分析报告

## 一、分析范围
## 二、总体健康结论
## 三、关键风险节点
## 四、薄弱节点原因分析
## 五、已挂载企业支撑情况
## 六、管理建议
## 七、数据口径说明
```

管理建议只围绕已挂载企业、节点治理、挂链核验、数据完善，不写外部补链招商名单。

```xml
    <artifactId>openhtmltopdf-pdfbox</artifactId>
    <version>1.0.10</version>
</dependency>
```

实现策略：

- Markdown 转 HTML 后保存到 `analysis_report_content.content_html`。
- HTML 外层套固定 CSS，保证预览与 PDF 一致。
- PDF 保存到后端本地目录，例如 `reports/analysis/{taskId}.pdf`。
- 目录路径放入配置项，例如 `analysis.report.storage-dir`。
- 下载接口返回 `ResponseEntity<Resource>`，设置文件名。

如果 PDF 依赖安装或中文字体处理来不及，第一阶段可先完成 Markdown 与 HTML，PDF 接口返回明确错误；但验收要求里包含 PDF，最终提测前需要补齐。

### 4.9 审计日志

以下接口加 `@OperationLog`：

- 创建报告：`action = "create_analysis_report"`
- 重试报告：`action = "retry_analysis_report"`
- 下载报告：`action = "download_analysis_report"`

详情查询和列表查询不建议记录，避免日志噪声。

```text

  -> COMPLETED 后展示 HTML
```

轮询停止条件：

- `COMPLETED`
- `FAILED`
- `CANCELLED`
- 组件卸载
- 超过最大轮询时长，例如 5 分钟

报告详情页：

- `PROCESSING`：显示进度状态和刷新按钮。
- `COMPLETED`：渲染 `contentHtml`，提供 PDF、Markdown 下载。
- `FAILED`：显示失败原因和重试按钮。
- `CANCELLED`：显示状态和重试按钮。

HTML 预览安全：

- 后端生成 HTML 时应进行 Markdown 渲染与必要清洗。
- 前端如使用 `v-html`，只渲染后端报告接口返回的可信 HTML，不渲染用户输入。

## 6. 后端关键 SQL 建议

### 6.1 查询选中节点的子树节点

```sql
SELECT child.id
FROM chain_node selected
JOIN chain_node child
  ON child.chain_id = selected.chain_id
 AND child.node_path LIKE CONCAT(selected.node_path, '%')
 AND child.is_deleted = 0
WHERE selected.chain_id = #{chainId}
  AND selected.id IN (...)
  AND selected.is_deleted = 0
```

需要去重，因为用户可能同时选择父节点和子节点。

### 6.2 查询子树企业画像

```sql
SELECT n.id AS node_id,
       e.id AS enterprise_id,
       e.enterprise_name,
       e.status,
       e.region,
       e.industry,
       e.main_products,
       e.core_tech,
       e.output_value,
       e.tax_amount,
       GROUP_CONCAT(t.tag_name ORDER BY t.id SEPARATOR ',') AS tag_names
FROM chain_node n
JOIN enterprise_node_rel r
  ON r.node_id = n.id
 AND r.is_deleted = 0
JOIN enterprise e
  ON e.id = r.enterprise_id
 AND e.is_deleted = 0
LEFT JOIN enterprise_tag_rel etr
  ON etr.enterprise_id = e.id
LEFT JOIN tag t
  ON t.id = etr.tag_id
 AND t.is_deleted = 0
WHERE n.chain_id = #{chainId}
  AND n.id IN (...)
  AND n.is_deleted = 0
GROUP BY n.id, e.id
```

### 6.3 查询历史推荐证据

```sql
SELECT mt.enterprise_id,
       mr.node_id,
       mr.confidence,
       mr.reason,
       mr.evidence,
       mr.decision,
       mt.created_at
FROM matching_result mr
JOIN matching_task mt
  ON mt.id = mr.task_id
WHERE mt.chain_id = #{chainId}
  AND mr.node_id IN (...)
  AND mr.decision IN ('ACCEPTED', 'PENDING')
ORDER BY mt.created_at DESC
LIMIT 100
```

历史推荐证据只作为说明材料，不影响健康分。

## 9. 风险与处理

| 风险 | 处理 |
| --- | --- |
| G6 v5 API 与原型使用的旧 `TreeGraph` 写法不一致 | 正式项目以安装版本文档为准，图数据转换与健康度计算保持独立 |
| PDF 中文字体乱码 | 配置中文字体文件，或先使用系统字体回退并在测试环境确认 |
| 通用 LLM 当前固定 `response_format=json_object` | 提示词要求返回 `{"markdown":"..."}`，由 `AnalysisReportResultParser` 提取 Markdown；后续如通用客户端支持自由文本再切换 |
| 子树企业统计 N+1 查询 | 诊断树接口批量查询，严禁每节点单独查企业 |
| 报告 Prompt 过长 | 风险节点优先、样本上限、摘要为主 |
| 前端 `v-html` 安全 | 后端统一 Markdown 渲染与清洗，前端只展示报告服务产物 |
| 权限未配置导致 403 | 迁移权限数据，或开发阶段临时复用 `chain:node:query` |

## 11. 第一版验收口径

1. 进入“产业链健康分析”页面后，可以选择产业链并展示 G6 树图。
2. G6 节点按后端健康等级渲染颜色，按健康分或企业数渲染大小。
