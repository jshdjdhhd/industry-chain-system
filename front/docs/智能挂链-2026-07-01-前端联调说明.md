## 页面行为

智能挂链页面当前按异步任务模式工作：

```text
点击智能推荐
        ↓
创建后端 matching_task
        ↓
前端轮询任务状态
        ↓
展示 matching_result 候选列表
        ↓
用户采纳 / 拒绝 / 人工改选
```

这样做的原因是后端可能需要执行 embedding 召回、规则计算、LLM rerank 和数据库写入，同步等待体验较差。轮询模式可以让页面展示任务状态，避免接口长时间阻塞。

## 今日重点改动

### 1. 低置信候选不再显示为空状态

之前当后端返回“没有达到自动推荐阈值”时，页面容易表现成没有候选，只提示用户人工选择。这个交互不利于人工复核。

现在页面会展示后端返回的低置信候选，并标注：

```text
低置信候选，不建议自动挂链；可作为人工复核备选节点。
```

判断规则在 `src/views/matching/matchingViewModel.ts` 中：

- `confidence < 0.65`
- 或推荐理由包含“不建议自动挂链”
- 或 `evidence` 包含 `LOW_CONFIDENCE`

### 2. 候选列表支持风险提示

候选列表现在会区分普通推荐和低置信候选：

- 普通推荐：正常展示节点、置信度和推荐理由。
- 低置信候选：使用风险提示样式，并显示“不建议自动挂链”的说明。

这样用户能看到候选，但不会误以为系统强烈推荐该节点。

### 3. 人工改选闭环完善

页面支持在推荐结果基础上人工改选节点。人工改选不是只改前端展示，而是会调用后端接口创建正式挂链关系。

交互定位如下：

- **采纳：** 接受当前推荐节点。
- **拒绝：** 拒绝待决策推荐结果。
- **人工改选：** 用户认为推荐不准时，手动选择其他节点并确认挂链。

### 4. 与后端低置信 evidence 对齐

后端低置信候选会在 `evidence` 中带上类似字段：

```json
{
  "recommendation_level": "LOW_CONFIDENCE",
  "below_min_result_confidence": true,
  "below_vector_threshold": true,
  "llm_skipped": true
}
```

前端不直接依赖完整 JSON 结构，只做兼容识别。这样即使后端为了适配远程数据库字段长度压缩 evidence，前端也能根据关键词和置信度给出正确提示。

## 联调注意事项

- 当前前端不再默认使用 mock 接口，联调时要确保后端 `8080` 正常启动。
- 智能推荐接口可能仍有一定耗时，前端通过轮询展示任务状态。
- 如果后端返回低置信候选，页面应该展示候选列表，而不是空状态。
- 如果用户点击拒绝时结果已经被采纳或处理，后端会拒绝二次操作，页面需要提示这是状态限制，不是接口不可用。
- 人工改选需要先读取产业链节点，否则用户没有可选节点。

## 给队友的理解重点

前端不要把“低置信”理解成“无结果”。当前产品逻辑是：

- 有高置信结果：正常推荐。
- 没有高置信结果，但有候选：展示低置信候选，提醒人工复核。
- 完全没有候选：再展示空状态，引导读取节点或人工选择。

这能避免智能推荐在不确定时直接让用户失去判断依据，也能避免低质量结果被包装成强推荐。
